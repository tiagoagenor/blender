# SketchUp Mode for Blender: Blender API Feasibility and Architecture

Target runtime: **Blender 5.2.2 LTS** (`/Applications/Blender.app`, macOS arm64, **Metal** GPU backend, **Python 3.13.13**).
Delivery: **Application Template**, pure Python, no C/C++ rebuild.
Reference sources: the bundled scripts in `/Applications/Blender.app/Contents/Resources/5.2/scripts/` and this repo's C sources (5.4 alpha) for internals.

> **How this was verified.** Every claim marked ✅ was executed on the installed 5.2.2, either headless (`--background --factory-startup`) or in a **GUI session driven by timers, with `bpy.ops.screen.screenshot`**. Simulated input used `--enable-event-simulate` and `Window.event_simulate`. The prototype scripts and screenshots are in the session scratchpad (see Appendix A). Claims marked 📖 come from reading the source or bundled scripts. Claims marked ⚠️ are recommendations or are unverified.

### Blockers and real limitations (not showstoppers)

1. **Blender meshes have no faces with holes.** SketchUp's "rectangle drawn inside a face" creates a face with an inner loop. In Blender you must split the outer face with **bridge edges** and hide those edges (§3.4). As a result, **edge display must be custom-drawn** (GPU batch), because the wireframe overlay would show the bridge edges. Phase 1 can use the overlay; phase 2 needs the custom edge renderer.
2. **Header regions have a fixed height** (about 26 px × UI scale). The top toolbar icons will be about 20 px, not SketchUp's 24–32 px. The left TOOLS region does show large icons, and it **switches to 2 columns automatically** when about 80–120 px wide (📖 `space_toolsystem_common.py`). That two-column layout is exactly SketchUp's Large Tool Set.
3. **No custom mouse-cursor bitmaps** from Python. Only built-in cursors are available: `CROSSHAIR`, `PAINT_CROSS`, `ERASER`, `EYEDROPPER`, `HAND`, `HAND_CLOSED`, `ZOOM_IN`, `KNIFE`, `MOVE_X`, … (✅ list in Appendix B). Workaround: `cursor_set('NONE')` and draw the cursor icon yourself in POST_PIXEL. It lags one frame.
4. **Solid mode has no real back-face material.** The face-orientation overlay gives a flat (unlit) blue-gray tint on back faces. This is good enough and verified ✅. A lit back-face colour would need Material Preview (EEVEE) plus a Backfacing node, which is slower.
5. **Global areas (TOPBAR, STATUSBAR) are not in `window.screen.areas`** ✅. They can't be reached with `temp_override(area=…)`. You can only change them through header class overrides.
6. **Changing UI layout inside the same timer tick as `area_close` / `area_split` can crash Blender** ✅ (segfault in `ED_area_init`, reproduced). Run layout mutations in separate ticks, or better, **ship a pre-built `startup.blend`** (§1.4).

## 1. App template structure

### 1.1 Folder layout (recommended)

```
SketchUp/                              # template id = folder name ("SketchUp" shown in File > New)
├── __init__.py                        # register()/unregister() – thin, delegates to package modules
├── startup.blend                      # generated by tools/build_startup.py (never hand-edited)
├── userpref.blend                     # OPTIONAL but recommended: scopes theme/keymap/addons to the template (§1.3)
├── presets/keyconfig/SketchUp.py      # full custom keyconfig (§6.3)
├── icons/                             # *.png (toolbar) and/or *.dat (toolsystem geometry icons)
├── su/                                # the actual Python package (see §11)
└── tools/build_startup.py             # script that builds startup.blend in a GUI Blender
```

Search order for templates (📖 `bpy.utils.app_template_paths`, ✅ tested):
1. `{BLENDER_USER_SCRIPTS}/startup/bl_app_templates_user/{id}`. On macOS the default is `~/Library/Application Support/Blender/5.2/scripts/startup/bl_app_templates_user/`.
2. Each path in **`$BLENDER_SYSTEM_SCRIPTS`** + `/startup/bl_app_templates_system/{id}`.
3. The bundled `…/Resources/5.2/scripts/startup/bl_app_templates_system/{id}`.

The template module is imported as `bl_app_templates_user.SketchUp` or `bl_app_templates_system.SketchUp`. Use **relative imports** inside the package.

### 1.2 `register()` / `unregister()` lifecycle (📖 `bl_app_template_utils.py`, ✅ tested)

* Only one template is active at a time. `bl_app_template_utils.activate()` calls `register()` when the template is enabled, at startup or through **File › New › SketchUp**. It calls `unregister()` when you switch to another template.
* **`register()` runs inside `RestrictBlend`.** `bpy.data` is replaced by `_RestrictData` (✅ printed `_RestrictData`). `bpy.context` only exposes `.preferences` and `.window_manager`. You may register classes, tools, keymaps and handlers, and change preferences. **Don't touch scenes or screens there.** Do that in handlers or timers instead.
* Handler order on startup (✅ observed): `load_post` fires first, then `load_factory_startup_post`. `load_factory_startup_post` fires **only** when the template's shipped `startup.blend` (or Blender's built-in factory file) is loaded. It does **not** fire when the user's own saved `{config}/SketchUp/startup.blend` is loaded. Bundled templates (2D_Animation, Video_Editing, …) use `load_factory_startup_post` for one-time "factory" fixes. Mark handlers with `@persistent`.
* **Use `load_post` for anything that must hold for every file**: draw handlers, ensuring the "SketchUp" workspace, fixing the shading of opened `.blend` files, invalidating caches.

```python
# SketchUp/__init__.py  (verified pattern)
import bpy
from bpy.app.handlers import persistent
from . import su   # package

@persistent
def _on_load_post(_):
    su.session.on_file_loaded()        # re-apply view settings, rebuild caches, ensure draw handlers

def register():
    su.register()                      # classes, tools, gizmos, keymaps, prefs (with backup)
    bpy.app.handlers.load_post.append(_on_load_post)
    bpy.app.handlers.exit_pre.append(su.prefs.restore_on_exit)   # see §6.2

def unregister():
    bpy.app.handlers.load_post.remove(_on_load_post)
    bpy.app.handlers.exit_pre.remove(su.prefs.restore_on_exit)
    su.unregister()
```

### 1.3 `startup.blend` and `userpref.blend` in templates (📖 `wm_files.cc`, `blender.cc`, ✅ tested)

**Startup file resolution with template `T`:**
1. `{USER_CONFIG}/T/startup.blend` (written by *File › Defaults › Save Startup File* = `bpy.ops.wm.save_homefile()`). ✅ `save_homefile` writes there when a template is active.
2. Otherwise `{template_dir}/startup.blend`. This counts as "factory", so `load_factory_startup_post` fires.
3. Otherwise Blender's built-in factory startup (all 11 default workspaces). ✅ observed.

For non-builtin templates, Blender does **not** reset panel layouts, region sizes or saved active tools (📖 `blo_update_defaults_screen` / `BLO_update_defaults_workspace` only reset these for builtin templates). So **region widths, the active sidebar tab ("Tray") and the active tool saved in your `startup.blend` persist.** ✅ The active tool and a shading change persisted across restarts.

**Template `userpref.blend` merges only a subset of preferences** (📖 `BKE_blender_userdef_app_template_data_swap`):
`themes, uistyles, uifonts, addons, user_keymaps, user_keyconfig_prefs, keyconfigstr (active keyconfig name), font paths, gizmo_flag, app_flag (show_corner_split / show_edge_resize / show_regions_visibility_toggle), ui_scale, uiflag: SAVE_PROMPT | SPLASH_DISABLE | SHOW_GIZMO_NAVIGATE`.

**Everything else comes from the user's main prefs**, including all of `prefs.inputs` (navigation) and most of `prefs.view`. Template code must set those values (§6.2).

If the template ships a `userpref.blend`, `BKE_appdir_app_template_has_userpref()` becomes true. On save, Blender then writes the template subset to `{USER_CONFIG}/SketchUp/userpref.blend` and the rest to the main file (📖 `BKE_blendfile_userdef_write_all`). **This keeps our theme and keymap from leaking into the user's normal Blender.** You can generate one by running Blender with `BLENDER_USER_CONFIG=/tmp/x`, applying the theme, running `bpy.ops.wm.save_userpref()`, and copying `/tmp/x/userpref.blend` into the template. It also gives us `SPLASH_DISABLE`, so there is no splash in SketchUp mode.

### 1.4 UI from code vs a binary `startup.blend`

Both work. **Recommendation: generate `startup.blend` from a script, commit the script, and treat the `.blend` as a build artifact.** Then add a light `load_post` "ensure" pass for things that must hold in any opened file.

* Creating the layout from code at runtime is possible (✅ `screen.area_split`, `area_close`, setting `area.type`, region toggles, `region.active_panel_category`). However, it is fragile: crash on same-tick mutation, region sizes only valid after a redraw, `area_join` needs pixel coordinates. It also flickers on every start.
* A `startup.blend` gives exact region widths, closed and open tray panels, the two-column toolbar, the initial camera, units, default materials and an empty scene.

**Programmatic build (✅ verified pieces):**

```bash
BLENDER_SYSTEM_SCRIPTS=$REPO/su_template_root \
BLENDER_USER_CONFIG=$TMP/cfg  BLENDER_USER_SCRIPTS=$TMP/scripts \
/Applications/Blender.app/Contents/MacOS/Blender --app-template SketchUp --python tools/build_startup.py
```

```python
# tools/build_startup.py  (pattern; each step in its own timer tick — required, see §0 blocker 6)
import bpy, os, shutil
STEPS = []
def step(fn): STEPS.append(fn); return fn

@step
def strip_workspaces():
    keep = bpy.data.workspaces["Layout"]
    win = bpy.context.window_manager.windows[0]
    win.workspace = keep
    # ✅ works (no bpy.data.workspaces.remove exists). Do NOT use bpy.ops.workspace.delete with
    # temp_override(workspace=ws): it ignores the override and deletes the window's ACTIVE workspace (verified).
    bpy.data.batch_remove([ws for ws in bpy.data.workspaces if ws != keep])
    keep.name = "SketchUp"

@step
def close_areas():
    win = bpy.context.window_manager.windows[0]; scr = win.screen
    for t in ('DOPESHEET_EDITOR', 'OUTLINER', 'PROPERTIES'):
        for a in [a for a in scr.areas if a.type == t]:
            with bpy.context.temp_override(window=win, screen=scr, area=a):
                bpy.ops.screen.area_close()     # ✅ FINISHED

@step
def configure_view():                           # ✅ must be a later tick than area_close
    win = bpy.context.window_manager.windows[0]
    area = next(a for a in win.screen.areas if a.type == 'VIEW_3D')
    sp = area.spaces.active
    sp.show_region_header = False               # SketchUp has no per-viewport header
    sp.show_region_tool_header = True           # → our horizontal "Getting Started" toolbar
    sp.show_region_toolbar = True               # → Large Tool Set (2 columns at ~100px)
    sp.show_region_ui = True                    # → Tray
    # … shading/overlay (§7), scene units, delete default cube/light/camera …

@step
def tray_tab():
    win = bpy.context.window_manager.windows[0]
    area = next(a for a in win.screen.areas if a.type == 'VIEW_3D')
    next(r for r in area.regions if r.type == 'UI').active_panel_category = 'Tray'

@step
def save():
    out = os.path.join(os.path.dirname(__file__), "..", "startup.blend")
    bpy.ops.wm.save_as_mainfile(filepath=out, copy=True)   # ✅ works; or save_homefile() → {USER_CONFIG}/SketchUp/
    bpy.ops.wm.quit_blender()

def run_next():
    if STEPS:
        STEPS.pop(0)()
        return 0.5
    return None
bpy.app.timers.register(run_next, first_interval=1.0)
```

> Region widths: `Region.width` is read-only. To set the TOOLS or UI width, drag in a GUI session once, or resize through `bpy.ops.screen.region_scale` (interactive). In practice: build with the script, open the result once in the GUI, adjust the widths, then save with `save_as_mainfile(copy=True)`. The widths persist (non-builtin templates don't reset `sizex`).

### 2.2 Full control of the left toolbar (✅)

`VIEW3D_PT_tools_active._tools` is a plain dict of `{mode: [ToolDef | None | tuple(group)]}`. A template may replace it entirely and restore it in `unregister()`:

```python
from bl_ui.space_toolsystem_toolbar import VIEW3D_PT_tools_active as TA
_saved = None
def install_toolbar(tooldefs_in_order):
    global _saved
    _saved = {k: list(v) for k, v in TA._tools.items()}
    TA._tools[None] = []                         # removes mode-independent tools (cursor etc.)
    TA._tools['OBJECT'] = tooldefs_in_order      # e.g. [select, None, line, (arc, arc2pt, pie), rect, circle, polygon, None, pushpull, ...]
def uninstall_toolbar():
    TA._tools.clear(); TA._tools.update(_saved)
```

* Each registered tool class exposes its `ToolDef` as `MyTool._bl_tool` after `register_tool`. ✅ used.
* A `tuple` makes a **flyout group**, like SketchUp's Arc / 2-Point Arc / 3-Point Arc / Pie. `None` makes a separator.
* Builtin tools such as `builtin.select_box` can be fetched from the saved lists and reused, but we will write our own Select.
* `tool_fallback_id = "builtin.select"` is a class attribute. Override it if the builtin select is not in our list.
* **Two-column Large Tool Set:** `_layout_generator_detect_from_region` uses 2 columns when the TOOLS region is 80–120 px wide (UI-scaled). Save that width in `startup.blend`.

### 2.3 Custom icons (✅ both methods)

1. **`.dat` geometry icons** (Blender's native toolbar format). `ToolSelectPanelHelper._icon_value_from_icon_handle` does `os.path.join(datafiles/icons, name + ".dat")`. **An absolute path in `bl_icon` wins in `os.path.join`**, so `bl_icon = "/abs/dir/su.line"` loads `/abs/dir/su.line.dat`. ✅ Produce `.dat` files from a `.blend` of flat-coloured meshes with `release/datafiles/blender_icons_geom.py` (in this repo: `blender icon_file.blend --background --python release/datafiles/blender_icons_geom.py -- --output-dir=…`). The format is 8-byte header "VCO" plus triangles and colours.
2. **PNG icons (simplest for SketchUp-like art):** load them into `bpy.utils.previews` and monkey-patch the icon resolver. ✅ It worked in both the left toolbar and the tool header.

```python
import bpy.utils.previews
```

(`bl_icon = "su.eraser"`.) Both menus and `layout.operator(..., icon_value=…)` accept preview `icon_id`s.

### 2.5 Keymaps per tool and single-key switches

* A tool's own keymap is `bl_keymap`, active only while that tool is active. It is evaluated **before** the editor keymaps.
* Global single-key switches are `wm.tool_set_by_id` items. **Where you put them matters.** For an Object-Mode 3D View, the handler order is roughly: tool keymap, then `Object Mode`, `Object Non-modal`, `3D View Generic`, `3D View`, `Frames`, `Screen`, `Window`. `M` in "Object Mode" (move to collection) would shadow an `M` placed in "3D View". Addon keymap items are inserted **at the head** of the matching user keymap (📖 `wm_keymap_addon_add` uses `BLI_addhead`; ✅ our `L` came first in "Object Mode").
* Quick approach: put the tool keys in `keyconfigs.addon` → `"Object Mode"`. Clean approach: a full keyconfig (§6.3).

## 3. Geometry model and modal drawing tools

### 3.1 Edit Mode vs Object Mode: recommendation

**Stay in Object Mode permanently. Keep each editable mesh as a cached `bmesh` owned by our "document" layer, and write it back with `bm.to_mesh(me)` after each operation.**

Why not Edit Mode:
* Edit Mode visuals don't look like SketchUp: vertex dots, edit colours, orange selection, face dots. Its selection model is component-based.
* Edit Mode is single or multi-object, and you can't click-select other objects (groups/components) while in it. SketchUp's top level mixes raw geometry and groups.
* Entering or leaving Edit Mode costs a full mesh conversion (each `mode_set`).

Object Mode plus a cached BMesh gives:
* Full control. Selection is stored in bmesh select flags or bool attributes and drawn by our overlay (blue edges, stippled faces like SketchUp).
* **Groups/Components = separate objects / collection instances.** "Edit group" = make that object the *edit context*: switch which cached bmesh tools write to, and dim the others with our own overlay or `overlay.show_fade_inactive`-like logic. This matches SketchUp's context model nicely.
* Undo: operators with `bl_options={'REGISTER','UNDO'}` push **memfile (global) undo** steps, which capture `to_mesh` changes. Invalidate the bmesh cache in `undo_post` / `redo_post` / `load_post` handlers.

Measured costs on a **160k-face mesh** (✅ headless 5.2.2):

| Operation | ms |
|---|---|
| `bm.from_mesh(me)` | 28.3 |
| `bm.to_mesh(me)` | 7.6 |
| `me.update()` | 0.2 |
| `BVHTree.FromBMesh(bm)` | 34.7 |
| 1000 × `bvh.ray_cast` | 0.85 total |
| 1000 × `bvh.find_nearest` | 2.25 total |
| `KDTree` build (Python loop, 160k) | 34.8 |
| 1000 × `kd.find_range` | 5.0 total |
| `vertices.foreach_get("co")` → numpy | 3.4 |
| numpy project 160k verts + nearest-to-cursor | 5.8 |

So a typical SketchUp-scale model (well under 100k faces) commits an edit in **under 10 ms**. Rebuilding acceleration structures **lazily** (only when the mesh changed and someone needs them) stays under 50 ms.

> If you ever need Edit Mode (e.g. power users), the fast path is `bmesh.from_edit_mesh(me)` plus `bmesh.update_edit_mesh(me, loop_triangles=False, destructive=False)` for coordinate-only changes. Use `True, True` after topology changes. The 5.2 signature is ✅ `update_edit_mesh(mesh, *, loop_triangles=True, destructive=True)`.

### 3.2 Modal tool pattern (✅)

```
Tool active (idle) ──► Gizmo.test_select on every MOUSEMOVE → inference → overlay   (§5.4)
LEFTMOUSE press   ──► tool keymap → su.line_modal.invoke() → modal_handler_add
modal(): MOUSEMOVE → inference; LEFTMOUSE → commit point; digits/ , . ; ' " m → VCB buffer;
         RET → apply VCB; ESC/RIGHTMOUSE → cancel;
         MIDDLEMOUSE / WHEEL* / TRACKPAD* / NDOF* → return {'PASS_THROUGH'}  (navigate while drawing)
```

* ✅ While the modal runs, `test_select` is **not** called (0 calls during modal), so the operator does its own inference on MOUSEMOVE using the same `InferenceEngine`.
* ✅ `event.unicode` delivers typed characters (`'1'`). Use it for the VCB and fall back to `event.type` for Enter and Backspace.
* SketchUp click-move-click needs `value == 'PRESS'` on the first click. Treat a press-drag-release as click-click too (SketchUp accepts both).
* Commit through one `su.core.document.commit(obj_key, bm, msg)` that calls `bm.to_mesh` and `me.update()`, then tags redraw. The operator returns FINISHED with `UNDO`, so there is exactly one undo step per SketchUp action. For multi-segment Line chains, push undo per segment with `bpy.ops.ed.undo_push(message=…)`, or make each segment its own operator run.

### 3.3 Auto face creation (✅)

* `bmesh.ops.edgenet_fill(bm, edges=…)` and `bmesh.ops.contextual_create(bm, geom=edges)` both produced the face from 4 loose edges. **Both returned the normal −Z for a CCW loop drawn on the ground.** That matches SketchUp, where faces on the ground show their back side up. Either way, **orient explicitly** by comparing `f.normal` with the desired normal and calling `bmesh.utils.face_flip(f)`, or use `bmesh.ops.reverse_faces`.
* After each new edge: find the **minimal coplanar cycles** through the new edge. Walk the planar graph in the edge's plane and pick the smallest-turn loops, then `bm.faces.new(loop_verts)` when the loop is closed and coplanar (tolerance about 1e-5 × model scale) and no face exists yet. Writing our own small planar-cycle finder is more predictable than `edgenet_fill`, which may fill the wrong region on complex nets. `edgenet_fill` is fine for a closed loop the tool knows it just closed (Rectangle, Circle, Polygon).
* **Splitting a face with a new edge across it:** `bmesh.ops.connect_vert_pair(bm, verts=[a, b])` ✅ (2 faces after it). Or use `bmesh.utils.face_split(face, v1, v2)`.
* **Splitting edges at intersections / inference points:** `bmesh.ops.bisect_edges(bm, edges=[e], cuts=1)` ✅, or `bmesh.utils.edge_split(edge, vert, fac)` for a single exact point. Then `bmesh.ops.remove_doubles` / `weld_verts`. Line-line intersection: `mathutils.geometry.intersect_line_line`.

### 3.4 Faces with holes (limitation; ✅ workaround tested)

* `bmesh.utils.face_split_edgenet(face, inner_loop_edges)` with **only** the inner loop returns **0 faces**. Islands are unsupported.
* With **one** bridge edge from the outer boundary to the inner loop it also failed (0).
* With **two bridge edges** (outer v0→inner v0 and outer v2→inner v2) plus the inner loop: ✅ 3 faces `[6, 6, 4]`, meaning the outer ring split into two hexagons plus the inner quad.
* **Plan:** mark bridge edges with a bool edge attribute `su_hidden` (`bm.edges.layers.bool.new("su_hidden")`; ✅ bool layers exist for edges and faces in 5.2). Do not draw these edges, never infer on them, and treat faces joined by hidden coplanar edges as **one logical face** for Select, Push/Pull, Paint and Entity Info. The same mechanism implements SketchUp **soft/smooth edges** (`su_soft`) and hidden edges.

### 3.5 Push/Pull, Offset, Follow Me, groups

* **Push/Pull** ✅: `ext = bmesh.ops.extrude_face_region(bm, geom=[face])`, then `bmesh.ops.translate(bm, verts=new_verts, vec=face.normal * d)` and `bmesh.ops.delete(bm, geom=[face], context='FACES_ONLY')` where SketchUp drops the original. Finish with `recalc_face_normals`. SketchUp specifics:
  * When pushing a face completely through a solid, delete it ("punch hole").
  * Ctrl = keep the original face (new start face).
  * Double-click = repeat the last distance.
  * Live preview: move the extruded verts each MOUSEMOVE and call `bm.to_mesh` (7 ms at 160k faces; much less for typical models). Alternatively, draw a GPU preview and only commit on click (cheaper).
* **Offset** ✅: `bmesh.ops.inset_region(bm, faces=[f], thickness=t, depth=0.0, use_even_offset=True, use_boundary=True)`. **`use_boundary=True` is required for an isolated face** (default False gave 0 new faces). `inset_individual` also works. Negative offset (outset) uses `use_outset=True`. Offset of selected **edges only** (not faces) needs custom code: offset a polyline in its plane with `geometry.intersect_line_line` at the corners.
* **Follow Me:** for circular paths use `bmesh.ops.spin(bm, geom=…, cent, axis, angle, steps, use_merge=True)` ✅ (lathe, 120 faces). For arbitrary paths, use a custom sweep. For each path vertex, compute a mitre frame (bisector plane of adjacent segments), project the profile onto that plane, build quads between consecutive rings, and cap if the path is open. This is about 150 lines of Python and fast enough.
* **Groups/Components:** a group is a separate mesh object (optionally parented to an Empty for nested hierarchies). A component is a **Collection** plus `Object(instance_type='COLLECTION', instance_collection=coll)`; all instances share geometry like SketchUp. "Make Unique" = copy the collection. Edit-in-context for components = edit the mesh inside the collection, and every instance updates. Use `obj.display.show_shadows`, `obj.color` and similar for display tweaks.
* **Intersect Faces** (later): `bpy.ops.mesh.intersect` requires Edit Mode. A pure-bmesh alternative is `bmesh.ops.bisect_plane` per face plane, or a temporary Edit-Mode excursion inside one operator.

### 3.6 Other bmesh ops confirmed present in 5.2.2 (✅)

`contextual_create, edgenet_fill, edgenet_prepare, triangle_fill, holes_fill, extrude_face_region, extrude_edge_only, inset_region, inset_individual, spin, bisect_edges, bisect_plane, connect_verts, connect_vert_pair, split_edges, dissolve_edges, dissolve_limit, remove_doubles, weld_verts, translate, create_vert, delete, recalc_face_normals, solidify, offset_edgeloops, join_triangles, planar_faces`. `face_split_edgenet` is **in `bmesh.utils`, not `bmesh.ops`**. `bmesh.utils` also has `edge_split, face_split, face_join, face_flip, vert_dissolve, vert_separate, vert_splice, edge_rotate`.

### 4.4 Performance rules for drawing

1. **Cache `GPUBatch` objects.** Rebuild only when the data changes: geometry version counter for the edge renderer, inference result for the snap marker. Build big batches from **numpy arrays** (`foreach_get` into `float32` arrays, then `batch_for_shader(sh, 'LINES', {"pos": arr}, indices=idx)`). ✅ `foreach_get` of 160k coordinates takes 3.4 ms.
2. Fetch shaders once at module import time, inside a GPU context. **Never call `gpu` functions in `--background`**: ✅ raises `SystemError … requires the gpu module to be initialized`. Guard with `if bpy.app.background: return`.
3. Use `region.tag_redraw()` on the one region under the mouse, not `area.tag_redraw()` for all areas, and only when the inference result actually changed.
4. Per object: `gpu.matrix.push_pop()` plus `gpu.matrix.multiply_matrix(ob.matrix_world)` instead of transforming vertices on the CPU.

### 4.5 Custom edge renderer (needed for hidden/soft edges and SketchUp "profiles")

* Build a batch per mesh of **visible** edges (exclude `su_hidden` and `su_soft`) with `POLYLINE_UNIFORM_COLOR`, black, width 1 px (or 2 px for profiles: silhouette edges whose adjacent faces face opposite directions relative to the view, computed in numpy on view change).
* **Z-fighting with faces:** mimic Blender's `GPU_polygon_offset` (📖 `gpu_matrix.cc`) by nudging the projection matrix:

  ```python
  win = rv3d.window_matrix.copy()          # mathutils is row-major: C winmat[3][2] == win[2][3]
  dist = 1.0 * 0.5                         # Blender halves 'dist' internally
  if rv3d.is_perspective:
      ofs = win[2][3] * -0.0025 * dist     # ≈ reduce z by 0.25%, exactly like GPU_polygon_offset_calc
  else:
      ofs = 0.00001 * dist * rv3d.view_distance
  win[2][3] -= ofs
  with gpu.matrix.push_pop_projection():
      gpu.matrix.load_projection_matrix(win)
      gpu.state.depth_test_set('LESS_EQUAL')
      batch.draw(shader)
  ```
  (⚠️ Not yet run on screen. Tune the amount empirically.)
* Phase 1 shortcut: `overlay.show_wireframes=True, wireframe_threshold=1.0, wireframe_opacity=1.0` plus theme `view_3d.wire = black`. ✅ This gives black edges on everything for free (g2 screenshot), but it **cannot hide** bridge or soft edges. `wireframe_threshold < 1` hides edges between coplanar faces, which also hides legitimate user-drawn coplanar splits.

## 5. Inference / snapping engine

### 5.1 Primitives (✅ present in 5.2.2)

* `bpy_extras.view3d_utils`: `region_2d_to_origin_3d`, `region_2d_to_vector_3d`, `region_2d_to_location_3d`, `location_3d_to_region_2d` ✅ (used in the gizmo test).
* `scene.ray_cast(depsgraph, origin, direction, distance=…)` → `(hit, location, normal, index, object, matrix)` ✅. It uses Blender's per-mesh cached BVH from the evaluated mesh runtime: **0.027 ms per call** in the hover test. It is the cheapest "what face is under the cursor" query, and it works for instances and modifiers too.
* `mathutils.bvhtree.BVHTree` ✅ `FromBMesh / FromObject / FromPolygons`, `ray_cast / find_nearest / find_nearest_range / overlap`.
* `mathutils.kdtree.KDTree` ✅ `insert / balance / find / find_n / find_range`.
* `mathutils.geometry` ✅ `intersect_line_line, intersect_line_plane, intersect_point_line, intersect_point_line_segment, intersect_ray_tri, closest_point_on_tri, distance_point_to_plane, intersect_plane_plane, normal, tessellate_polygon, delaunay_2d_cdt, convex_hull_2d, …`

### 5.2 Recommended design (fast, SketchUp-like)

Run a pipeline per mouse move. Target: **under 1 ms typical, under 4 ms worst case**, with all heavy data cached.

1. **Ray-cast** the scene (`scene.ray_cast`). This gives the face under the cursor (object, polygon index, hit point, normal).
2. **Local candidates first (SketchUp behaviour):** take the verts and edges of the hit polygon plus its neighbours from the cached bmesh (polygon index → `bm.faces[i]`, with `ensure_lookup_table` done once per rebuild).
   * **Endpoint:** project each vert with `location_3d_to_region_2d`. Accept it if within R_v = 12 px × ui_scale. Shown as a green dot.
   * **Midpoint:** the edge midpoint within R_v. Cyan dot.
   * **On Edge:** screen-space distance from the cursor to the projected segment within R_e = 8 px. Map back to 3D with `intersect_line_line(ray, edge)`. Red square.
   * **On Face:** the hit point. Blue diamond.
3. **Global screen-space cache for edges and verts not under the cursor** (the cursor is near an edge that has nothing behind it). On *view change* (detect `rv3d.perspective_matrix` changed), project **all** visible verts with numpy (✅ 5.8 ms per 160k), bucket them in a 2D grid (cell = 16 px), and store edge AABBs in the same grid. Each mouse move then looks up 9 cells, which is O(1). Rebuild lazily on the first mouse move after the view settles; during navigation, don't infer at all.
4. **Occlusion:** a vertex or edge candidate counts only if its depth is ≤ the ray hit depth + ε, or if the ray hit nothing.
5. **Axis inference** (from the tool's last point P0, or a hovered "inference point"): for each axis a ∈ {X red, Y green, Z blue} (or the active group's or custom axes), compute `intersect_line_line(ray_origin, ray_origin+ray_dir, P0, P0+a)`. This gives the closest point Q on the axis line. If `|project(Q) − mouse| < R_axis (≈ 10 px)`, lock to Q and draw a solid line P0→Q in the axis colour with the tooltip "On Red Axis". SHIFT locks the current inference; arrow keys force an axis (→ red, ← green, ↑ blue, ↓ parallel/perpendicular).
6. **Parallel/perpendicular to edge:** same test with the direction of the last hovered edge(s). Magenta line, "Parallel to Edge" / "Perpendicular to Edge".
7. **"From point" inference** (dotted lines): keep a small ring buffer (3–5) of recently hovered endpoints and midpoints with a hover-time stamp. SketchUp activates a point after about 0.5 s of hover. Test axis lines through each as in step 5 and draw a dotted line from the source point.
8. **Drawing plane** when nothing snaps: the plane of the hovered face if the first click was on a face, otherwise the ground plane z=0 (`intersect_line_plane`). For Rectangle/Circle, also lock to the axis-aligned plane chosen by inference, as SketchUp does (red, green or blue plane).
9. **Priority:** Endpoint > Midpoint > Intersection > On Edge > axis lock > On Face > free plane. If the user holds Shift on an inference, keep it.

### 5.3 Alternative for very large scenes (phase 2)

**GPU picking** (the approach used by CAD Sketcher). Render vertex and edge IDs as colours into a `gpu.types.GPUOffScreen` on view change, then read a small window around the cursor with `framebuffer.read_color(x-r, y-r, 2r, 2r, 4, 0, 'UBYTE')`. Occlusion is free (depth test) and the cost is O(1) per mouse move. It costs a GPU→CPU sync per read; reading 25×25 px is fine.

### 5.4 Hover inference without clicking: tool gizmo (✅)

* `WorkSpaceTool.bl_widget = "SU_GGT_inference"` points to a Python `GizmoGroup` (`bl_space_type='VIEW_3D'`, `bl_region_type='WINDOW'`, `bl_options={'3D'}`) with one Python `Gizmo`.
* **Don't set `'TOOL_INIT'`.** It postpones gizmo creation until the tool *operator* runs. ✅ With it the group never initialised; without it `setup()` ran.
* `Gizmo.test_select(self, context, location) -> int` is called on **every** mouse move while the tool is idle (✅ 40 calls for 40 moves). Run the inference there, store the result in the shared state, `region.tag_redraw()`, and **return -1** so the gizmo never "grabs" the mouse.
* `Gizmo.draw(self, context)` can draw with `gpu` directly. You can also draw from the global POST_VIEW handler, which is preferable since it is shared with the modal.

### 7.2 Sky and ground with a true horizon: recommended approach (✅ prototype g3)

Options considered:

| Option | Verdict |
|---|---|
| Theme gradient `LINEAR` (✅ works, g2 screenshot) | A vertical gradient across the *viewport*, unrelated to camera pitch. No ground. A quick fallback. |
| `shading.background_type='WORLD'` | Solid mode uses only the world's flat colour. No gradient. |
| Material Preview with a world Sky Texture | A real sky, but EEVEE. Too heavy, and the look is wrong. |
| PRE_VIEW full-screen gradient | ❌ Overwritten by the overlay engine's background (✅ tested). |
| **POST_VIEW full-screen quad at NDC z≈1 with depth test `LESS_EQUAL`** | ✅ **Recommended.** It only fills pixels where nothing was drawn (depth = 1). The horizon line is computed from the camera, so sky and ground move correctly when orbiting. |

```python
SKY_TOP=(0.45,0.66,0.88,1); SKY_HOR=(0.82,0.90,0.97,1); GND_HOR=(0.80,0.79,0.76,1); GND_BOT=(0.66,0.65,0.62,1)
_sh = gpu.shader.from_builtin('SMOOTH_COLOR'); _cache = {"key": None, "batch": None}

def horizon_ndc_y(rv3d):
    fwd = -(rv3d.view_matrix.inverted().col[2].xyz)               # view direction
    if rv3d.is_perspective:
        h = Vector((fwd.x, fwd.y, 0.0))
        if h.length > 1e-6:                                         # vanishing point of the horizontal direction
            c = rv3d.window_matrix @ rv3d.view_matrix @ Vector((h.x, h.y, 0.0, 0.0))
            if c.w > 1e-9: return c.y / c.w
    return -1.0 if fwd.z > 0 else (1.0 if fwd.z < -0.999 else 0.0) # ortho / straight up/down fallback

def draw_sky_ground():                                              # POST_VIEW
    rv3d = bpy.context.region_data
    if rv3d is None: return
    y = max(-1.2, min(1.2, horizon_ndc_y(rv3d)))
    if _cache["key"] != round(y, 4):                                # rebuild only when the horizon moved
        Z = 0.999999
        pos = [(-1,y,Z),(1,y,Z),(1,1,Z),(-1,1,Z), (-1,-1,Z),(1,-1,Z),(1,y,Z),(-1,y,Z)]
        col = [SKY_HOR,SKY_HOR,SKY_TOP,SKY_TOP, GND_BOT,GND_BOT,GND_HOR,GND_HOR]
        _cache["batch"] = batch_for_shader(_sh, 'TRIS', {"pos": pos, "color": col},
                                           indices=[(0,1,2),(0,2,3),(4,5,6),(4,6,7)])
        _cache["key"] = round(y, 4)
    with gpu.matrix.push_pop(), gpu.matrix.push_pop_projection():
        gpu.matrix.load_identity(); gpu.matrix.load_projection_matrix(Matrix.Identity(4))
        gpu.state.depth_test_set('LESS_EQUAL'); gpu.state.depth_mask_set(False)
        _cache["batch"].draw(_sh)
        gpu.state.depth_test_set('NONE')
```

* ✅ The model and the overlay axis lines remain visible on top (g3 screenshot).
* Register this handler **first**, so later POST_VIEW handlers (inference) draw over it.
* SketchUp's ground is optional ("Ground" in Styles › Background). Make the colours and toggles configurable in the Styles tray panel. Assume no camera roll (turntable). With roll, compute the horizon from two horizontal directions and draw a rotated quad.
* Colours: the theme background colour is used as the "clear" colour. Set it close to the horizon colour so any one-frame gap isn't noticeable.

## 8. Hiding Blender clutter, and the Tray

### 8.1 How bundled templates do it (📖)

2D_Animation, Sculpting, Storyboarding and Video_Editing do **almost nothing in code**. Their UI lives in `startup.blend`, and `__init__.py` only fixes a few space settings in `load_factory_startup_post`. The VFX template has only a `startup.blend`. ## 9. Status bar hint text and Measurements box (VCB)

* `context.workspace.status_text_set(text | None | callable)` ✅. The 5.2 docstring: *"When text is a function, this will be called with the (header, context) arguments."* Each tool can therefore install its own status draw function while active (left: hint, right: VCB) and clear it with `None` on exit.
* Alternatively, override `STATUSBAR_HT_header.draw` globally (✅ g2 screenshot shows "Select start point. Ctrl = toggle copy" on the left and "Length [1.25m]" on the right). The global override is better because the VCB must be visible even when no modal operator is running, as in SketchUp.

```python
def statusbar_draw(self, context):
    st = su.core.state.STATE
    layout = self.layout
    row = layout.row(align=True)
    row.label(text=st.hint, icon_value=su.icons.get(st.hint_icon))     # SketchUp: tool icon + instruction
    layout.separator_spacer()
    layout.template_reports_banner(); layout.template_running_jobs()
    layout.separator_spacer()
    row = layout.row(align=True); row.alignment = 'RIGHT'
    row.label(text=st.vcb_label)                                         # "Length" / "Distance" / "Angle" / "Sides" …
    sub = row.row(); sub.ui_units_x = 8
    sub.prop(context.window_manager.su, "vcb_text", text="")             # display + click-to-edit
bpy.types.STATUSBAR_HT_header.draw = statusbar_draw
```

* **Typing into the VCB:** SketchUp types into the VCB without focusing it. The active modal operator receives keys first (✅ `event.unicode == '1'`). Append to `STATE.vcb_buffer`, mirror it to `wm.su.vcb_text` for display, and on `RET` / `NUMPAD_ENTER` parse it. Redraw the status bar with `context.window.screen` tag or `for a in screen.areas` (global areas aren't listed), or simply `context.workspace.status_text_set` / `bpy.context.window_manager.update_tag()`. Rendering the field through a WindowManager property updates automatically when the property changes.
* **After the tool finished** (SketchUp lets you type a new length right after a click to re-do the last segment): keep a `last_action` record in the state, and let a lightweight "VCB listener" handle it. That listener is the tool's keymap item for `TEXTINPUT`/digits invoking `su.vcb_apply`, which re-executes the last op with the new value (undo + redo).
* **Parsing** ✅ `bpy.utils.units.to_value('METRIC','LENGTH', "1.25m") → 1.25`, `"125cm" → 1.25`, `('IMPERIAL','LENGTH', "5'6\"") → 1.6764`, `"2*3+1" → 7.0`. Divide by `scene.unit_settings.scale_length`. Formatting: `units.to_string('METRIC','LENGTH', 1.2345, precision=3) → "1.23 m"`. Multi-value input `"3m,2m"` (Rectangle) or `"12s"` (polygon sides): split on `,` / `;` first.

## 10. 5.x pitfalls and performance guidance

**API changes and gotchas (relevant here):**
* `bgl` is gone. Use `gpu.*` only, and the shader names in §4.1 (no `2D_`/`3D_` prefixes). Thick lines need `POLYLINE_*`, and `line_width_set` has no effect on Metal.
* `blf.size(fontid, size)` takes no dpi argument.
* `context.temp_override(window=…, area=…, region=…)` is required for operator context overrides. Dict overrides were removed in 4.0.
* `bpy.data` is unavailable in template `register()` (`RestrictBlend`). Defer to `load_post`, `load_factory_startup_post` or `bpy.app.timers`.
* **Don't mutate area/region layout in the same tick as `area_close` / `area_split`** (✅ crash). Areas created by `area_split` report `width=0` until the next redraw.
* Global areas (TOPBAR, STATUSBAR) are not in `screen.areas` ✅. Use `screen.show_statusbar` and header overrides.
* `bpy.ops.workspace.delete()` ignores `temp_override(workspace=…)` and deletes the **active** workspace ✅. Use `bpy.data.batch_remove([...])` ✅.
* `GizmoGroup` `bl_options` `'TOOL_INIT'` postpones setup until the tool operator runs (✅ trap).
* `gpu` in `--background` raises `SystemError` ✅. Guard every draw-module import or initialisation.
* Extensions (4.2+) don't cover app templates. Templates stay plain folders. Add-ons that the template depends on must be bundled as packages inside the template, not as extensions.
* `bmesh.ops.edgenet_fill` / `contextual_create` may produce −Z normals. Orient explicitly ✅.
* `inset_region` needs `use_boundary=True` for isolated faces ✅.
* `face_split_edgenet` cannot create holes ✅. Use two bridge edges plus the `su_hidden` attribute.
* Template preferences: only a subset is template-scoped (§1.3). Restore everything else in `exit_pre` ✅ (ordering verified in source).
* Python 3.13 ✅. Keep pure-Python dependencies vendored (numpy is bundled ✅).

**Performance rules:**
1. **Never call `bpy.ops` inside mouse-move paths.** Use bmesh, mathutils and numpy directly. Each `bpy.ops` call has a context, undo and notifier cost.
2. **No mode switching** during tools (Object Mode only).
3. **Cache, version and invalidate:** each `Document` (per edited mesh) holds `bm`, a `geom_version` counter, and lazily built `bvh`, `kd`, `edge_batch`, `screen_grid` (keyed by `geom_version` plus the view matrix hash). Invalidate on commit, `undo_post`, `redo_post`, `load_post`, and on `depsgraph_update_post` for objects we didn't change ourselves (e.g. the user used Blender's own ops).
4. **Don't infer during navigation.** Skip when `event.type` is MIDDLEMOUSE, a trackpad gesture, or a wheel event, and while `rv3d.view_matrix` changes frame to frame. Recompute when the view settles.
5. **Redraw only on change.** Tag `region.tag_redraw()` only if the inference result or the rubber band changed.
6. **numpy plus `foreach_get`/`foreach_set`** for any per-vertex or per-edge pass (projection, profile edges, batch building). Avoid Python loops over bmesh elements when the count can exceed about 10k.
7. Live previews (Push/Pull, Move) should **move existing verts** (`bmesh.ops.translate` plus `to_mesh`) instead of rebuilding topology on every mouse move. For Move/Rotate/Scale of whole groups, change `matrix_world` only, which costs nothing.
8. Big models: per-object documents, so editing one group doesn't rebuild caches for the whole scene. Components are collection instances, which share mesh data and are drawn by Blender's instancing.

**Interfaces that let several developers work in parallel:**
* `core.state.STATE`: the only shared mutable UI state. Tools write to it, and `draw/*` and `ui/statusbar.py` read from it.
* `core.inference.InferenceEngine.query(...) -> Inference`: one function signature. Tool authors can start with a stub that returns on-ground-plane points.
* `core.document.Document`: `get(obj)`, `.bm`, `.commit(msg)`, `.version`, `.invalidate()`. Tools never call `to_mesh` directly.
* `tools/base.SUModalTool`: subclass hooks `on_click(inf)`, `on_move(inf)`, `on_vcb(values)`, `hint()`, `vcb_label()`. They contain no event plumbing.
* `draw/handlers.py` layer registration `add_layer(name, fn, order)`, so each draw module is independent.

**Suggested work split:**
* (1) Template, startup, prefs, keymap, theme and UI shell.
* (2) Core document and geometry: auto-face, holes, splits.
* (3) Inference engine, spatial caches and inference drawing.
* (4) Drawing tools: Line, Arc, Rect, Circle, Polygon.
* (5) Modify tools: Push/Pull, Offset, Follow Me, Move, Rotate, Scale, Eraser, Paint.
* (6) Tray panels, groups and components, Scenes, Styles, Shadows.
* (7) Measure tools: Tape, Protractor, Dimension, Text.

Milestones: M1 = shell + navigation + look; M2 = inference + Line + auto-face; M3 = Rect, Circle, Push/Pull; then the rest.
